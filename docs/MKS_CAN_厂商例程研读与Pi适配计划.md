# MKS CAN 厂商 STM32 例程研读与 Pi 适配计划

日期：2026-09-01  
状态：已研读第一轮；作为 MKS CAN 驱动的主要代码参考，不直接复制 STM32 工程。

## 1. 材料与结论

来源为桌面目录 `08_例程-STM32系列(CAN)` 中 15--27 号 ZIP，以及 MKS CAN V1.0.9 手册。例程是厂商的 STM32F1 单轴演示，手册补充了例程没有覆盖的五轴同步、回零、限位和配置语义。

确认的共同协议行为：

- 发送 **标准 CAN 11-bit 帧**；电机地址直接作为标准 CAN ID。
- 帧末 CRC（例程的 `canCRC_ATM`）为 `CAN_ID + CRC 前所有数据字节` 的低 8 位。
- STM32 `CanTransfer()` 接收“预留最后一字节”的缓冲区，并在发送前填入 CRC。
- `F4`/`F5`/`FD` 的首次应答状态 `1` 为开始、随后状态 `2` 为完成；`3` 是触碰限位停止。
- 例程均使用一个 `CAN_RxDone` 全局标志和同步等待。这适合单轴教学，不适合作为五轴 Pi 运行时实现。

这与 `lamp_core/mks_can_protocol.py` 已实现的标准 ID、累加 CRC、`0x31`、`0x32`、`0xF3`、`0xF5`、`0x4A/0x4B` 帧一致。其字节向量由离线测试固定，当前不会连接 CAN 设备。

## 3. 对五轴台灯的实际适配

厂商例程只让一台电机发命令、阻塞等待一个完成状态。台灯必须改为：

    Behavior / teach recording
        -> SafetyGate（已回零、限位、许可、目标有效）
        -> joint rad -> 每轴已标定 encoder coordinate
        -> 五个 F5 目标帧分别发送
        -> 广播 0x4B 同步执行
        -> 接收队列按 (CAN ID, 功能码) 分派到五轴状态机
        -> TelemetryStore / Motion completion

启用同步标志后，先向各节点发送 `0x4A 0x01`；每个轴收到自己的 `F5` 后保持等待；最后用 CAN ID `0` 广播 `0x4B` 才共同开始。不同目标因此可以同步启动。这是手册明确提供的功能，不是自行设计的同步猜想。

`F5` 是优先路径：它使用累加多圈编码器坐标、支持绝对目标且支持运行中更新。若以后 MechanicalArm 的 Cartesian 100 Hz 外环经过五轴 IK、单位、增益和延迟实测验证，可将每次参考点转换成新的 F5 目标；`F6` 速度模式作为第二条候选执行路径，不预设为默认。

## 4. STM32 到 Pi 的替换边界

| STM32 示例部分 | Pi 3B CAN HAT 对应实现 | 适配理由 |
|---|---|---|
| `CAN_INIT()` 的 STM32 时钟、引脚和过滤器 | Linux SocketCAN 的 `can0` 配置 | HAT 已提供 CAN 控制器/收发器，Pi 不运行 STM32 外设代码 |
| CAN RX 中断 + `CAN_RxDone` | 单一收帧任务 + 有界队列 + ID/命令分派 | 五轴可并发返回，不能用一个布尔标志覆盖帧 |
| `waitingForACK()` 阻塞循环 | 每条请求的 deadline 与状态机 | 电机完成等待不能阻塞语音、监控或其它轴的反馈 |
| `CanTransfer()` | `mks_can_protocol.py` 编码 + 未来 `MKSCanDriver` SocketCAN 发送 | 保留厂家 CRC 和字节顺序，替换硬件 API |
| LED 无限闪烁错误循环 | `FAULT_LATCHED`、遥测日志、硬件急停链路 | 错误必须对五轴统一处理且可诊断 |
