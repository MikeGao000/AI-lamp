# MechanicalArm_Code_V2 与 SmallRobotArm 电机控制审阅

研究日期：2026-09-01。本文根据两个仓库 `main/master` 分支的公开代码编写；只提炼架构和算法，不复制其源代码、许可文本或特定驱动器帧。

## 结论先行

**MechanicalArm_Code_V2 的思路值得借鉴，接口不可直接复用。**它使用 STM32F407 经 CAN 控制 6 个带减速器的闭环步进节点：上位机只发送末端六维位姿；STM32 每 10 ms 读编码器位置、做逆运动学与轨迹跟踪、再向每个节点发送速度命令。

**SmallRobotArm 不应融合到底层。**它是 Arduino Mega 直接向六个开环驱动器产生 `STEP / DIR / EN` 脉冲，且用软件忙等待产生微秒延迟。它对于理解“角度—传动比—脉冲数”的换算有参考价值，但不适用于 CAN 智能闭环 MKS，且不具备编码器反馈、CAN 故障、现代安全状态机或可中断的实时队列。

我们的最终形态仍是：

```text
Pi：视觉、AI、动作语义、较慢的轨迹规划、日志/网页
      ↓ CAN（已验证的 MKS 协议）
MKS：编码器、FOC、电流/位置闭环、本轴加减速
      ↓
5 轴灯体
```

不需要为了模仿 MechanicalArm 再添加 STM32；只有在改成普通 STEP/DIR 驱动器、或实测 MKS 无法提供同步短轨迹时，STM32 才有必要成为实时脉冲控制器。

## 1. MechanicalArm_Code_V2：实际控制链路

```text
串口输入：x,y,z,alpha,beta,gamma
         ↓
STM32F407：正解得到当前末端位姿 → S 曲线笛卡尔插值
         ↓ 每 10 ms
CAN 读各闭环节点当前位置 → 逆解选择最接近当前姿态的解
         ↓
前馈关节速度 + P 位置误差补偿 → 每轴 RPM
         ↓
CAN 速度命令 → 闭环步进节点内部执行
```

### 证据与细节

- `Core/Src/tim.c` 将 168 MHz 时钟分频到 10 kHz、周期 100，对应 100 Hz（10 ms）。`Trajectory_Planning` 也写死 `CONTROL_DT=0.01`。
- `NewBee::UpDate()` 每个周期先查询电机位置、更新当前关节角，再对当前笛卡尔参考点做逆解，最终给六轴发送 `Motor_VelControl()`。
- `MotorControl::Motor_VelControl()` 将关节转速乘以每轴硬编码减速比（50/51/27 等）后发 CAN；`Motor_PosControl()` 则支持位置模式、脉冲数、相对/绝对标志和同步标志。
- CAN 报文并非 CANopen、也不是 MKS SERVO42D 的公开协议：它以扩展 CAN ID 编码地址与分包号，数据内使用项目对应节点的功能码，例如 `0xF6`、`0xFD`、`0x36` 和结尾字节 `0x6B`。**不得发送给 MKS。**
- 位置读回被转换为电机角度，再除以减速比、叠加 DH 零位偏置，才得到关节角。这个“电机坐标 → 减速传动 → 关节坐标”的分层是正确的。

### 该项目的优点

1. 真实读取编码器而非盲目累计步数。
2. 多轴读回后再计算，让逆解倾向当前姿态，降低姿态跳变。
3. 在 CAN 层已有多机同步启动概念。
4. S 曲线以笛卡尔路径插值，而不是让各轴独立到终点。

### 不能照搬的点与发现的问题

| 项目做法 | 风险/问题 | 我们的处理 |
|---|---|---|
| 每 10 ms 轮询全部轴并发送速度 | Pi 3B + CAN HAT 与未知 MKS 帧不保证时序；总线负载与响应时间尚未实测 | 先使用 MKS 内建位置/速度/加速参数；只在经手册确认的频率下进行状态轮询 |
| 用硬编码 `PID_Kp` 做外环速度 P 补偿 | 机械尺寸、减速比、负载不同，外环可能和 MKS 内部闭环打架 | 第一版不做 Pi 外环 PID；只做跟踪误差看门狗 |
| `CP_Ref[1024]` 固定数组 | 长动作可能超界；零距离路径的代码还可能继续使用 `s/S` | 我们用动态 Python 列表；零位移只返回一个点 |
| CAN 等待条件只检查前 5 轴标志，但代码控制 6 轴 | 会用到第 6 轴陈旧反馈 | 我们的反馈验证要求每个配置关节都有新报告 |
| 速度命令加速度参数为 0 | 注释说明为直接启动，可能不平滑 | 规划层同时限制峰值速度和峰值加速度 |
| 无独立硬限位/急停状态机 | 软件停机不能代替硬件 | 继续保留 NC 限位、硬件急停、`SafetyController` |

## 2. SmallRobotArm：实际控制链路

```text
Arduino Mega 中预设一组末端/关节动作
       ↓
解析逆运动学，得到 6 个关节角
       ↓
角度 ÷ (200 步/圈 × 32 微步 × 减速比) = 应发脉冲数
       ↓
软件循环 digitalWrite(STEP) + delayMicroseconds()
```

- `Simple6DoF_Ver2.ino` 固定分配了每轴 `PUL`、`DIR`、`EN` GPIO。
- 它以每轴的步距角、32 微步、减速比计算 `dl1..dl6`（每个脉冲对应的关节角）。
- `goStrightLine()` 在关节空间做梯形速度轨迹；`goTrajectory()` 对每轴顺序发脉冲。
- 它通过内存变量 `curPos*` 推断位置，没有读回编码器；失步后位置会永久漂移。

### 值得保留的概念

- 每轴都需要明确定义：方向符号、传动比、零位偏置、每输出单位对应的实际关节角。
- 动作不是跳到终点，而是经过时间参数化轨迹。
- 初始折叠姿态与工作姿态应分开，并在首次启用时低速验证。

### 不采用的部分

- GPIO `STEP/DIR/EN` 与微秒忙等脉冲生成。
- 无编码器的 `curPos` 作为真实位置。
- 逐轴阻塞循环；它会使急停、视觉和通信响应被延迟。
- 其几何、DH 参数、传动比和关节方向；它们只属于该 6DoF 机械臂。

## 3. 已融合进本项目的代码

### 多轴平滑轨迹：速度 + 加速度双限制

[`lamp_core/motion.py`](../lamp_core/motion.py) 原先已有更适合互动台灯的五次 minimum-jerk 曲线。本轮新增每轴 `maximum_acceleration_rad_s2`：轨迹时长同时满足峰值速度和峰值加速度限制，所有轴仍同步开始、同步结束。

这吸收了两项目“不要骤起骤停”的意图，但不复制其梯形或正弦 S 曲线实现。

### 闭环反馈看门狗

新增 [`lamp_core/feedback.py`](../lamp_core/feedback.py)：

```text
计划参考姿态 + MKS 读回位置
        ↓
每个动作段边界/健康任务检查：
  - 每轴都有报告
  - 报告未过期
  - 节点无故障
  - 实际角度与参考角度的误差未超限
        ↓
任一失败 → 反馈错误 → 未来 CAN 适配器上报 SafetyController.fault()
```

这是从 MechanicalArm 的位置轮询借来的安全思想，但刻意不做未标定的 Pi 外环 PID。MKS 的编码器位置环/FOC 应继续留在电机里。

## 4. 还不能“融合”的最后一层

真实 MKS CAN 适配器仍被故意阻断，因为当前没有你实际购买的 `MKS SERVO42D CAN` 的固件号与随货 CAN 手册。下面信息到位后才能实现 `prepare_move()`、`start_prepared_move()`、`cancel_motion()` 和反馈解析：

1. 淘宝商品链接或电机标签正反面；
2. 卖家提供的 PDF/压缩包中的 CAN 手册；
3. 实物 CAN 波特率、节点地址设置、位置单位、同步模式、急停/使能命令；
4. 单轴零位、方向、软限位和允许速度/加速度实测值。

在此之前，任何直接照抄 `0xF6`、`0xFD` 或 SmallRobotArm 脉冲引脚的“真实驱动”都不可靠且有损坏风险。
