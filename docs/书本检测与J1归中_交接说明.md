## 1. 任务与本轮目标

**任务**：智能台灯用 Pi 相机找到桌上的绘本，并用 J1（水平旋转轴）把书转正、居中、然后保持住。

**本轮实际做的事**：把"找书 + 居中"这条链路的检测层和控制层修复并稳定下来。核心结论是：

- **检测层换成本地 PP-OCR 文字检测**（2.4 MB ONNX，`cv2.dnn`，约 0.3 s，零成本、可离线），云端 VLM 降为兜底。
- **控制层修掉 7 个真实缺陷**，其中 4 个是"该动的时候冻住 / 该停的时候跑飞"这一类。
- 测试从 63 增加到 **161 个，全部通过**。

**当前实测状态**（重启后连续 48 秒）：

```

t=08s→t=16s  err=-0.01  motor 冻结在 +2.7   bbox 稳定  score=0.201
t=20s  锚点刷新（换到较小的文字块）err=-0.26 aim=+8.00 → 一步修正
t=24s→t=36s  err=-0.00  motor 冻结在 +14.8  score=0.091
```

获取+归中约 4~9 秒完成，稳态误差落在 1.3° 死区内、电机完全静止、无云端调用。

## 3. 检测层选型：实测依据（为什么不是 YOLO / 不是色差）

### 3.1 PP-OCRv3 文字检测（采用）

- 模型：`models/text_detection_en_ppocrv3_2023may.onnx`（2.4 MB，OpenCV Zoo `text_detection_ppocr`）
- 真实清晰帧上：`conf=0.98` 命中 `"Må jeg pynte kagen,"`、`conf=0.98` 命中 `"mor?"`，位置分毫不差；640px 下达 0.99，并正确检出显示器任务栏小字。
- 耗时（Pi 3B）：**320px ≈ 0.30 s、480px ≈ 0.60 s、640px ≈ 1.15 s**。
- ⚠️ **必须施加 PaddleOCR 归一化**：`setInputMean((123.675,116.28,103.53))` + `setInputScale(1/255/std)`。第一版漏了这一步，网络吃的是 0~255 原始像素，输出全是噪声（已写成回归测试）。
- ⚠️ 输入必须 3 通道；必须是 32 的倍数；按长边等比缩放（勿拉伸成正方形）。

### 3.2 COCO 的 `book` 类（否决）

- **公平复测**（清晰无拖影帧）：YOLOX-nano@416 → `book` 仅 **0.37~0.39**，且同时 `tv 0.37~0.40`、`cup 0.39`、`tie 0.35` 同档，**无区分度**。
- 此前曾在**严重拖影**的坏帧上得出"0.28~0.34"的结论，那张帧人眼也读不出字。已用清晰帧重测，**结论不变**。
- ⚠️ 本项目的 YOLOX ONNX 导出**输出原始 logits，需要显式 sigmoid**，否则框和分数都是垃圾。

### 3.3 网络上的现成书本权重（不存在可用的）

Hugging Face object-detection 索引按 `book` 检索，全世界只有 4 个，全是别的任务：书脊检测（书架）、藏文古籍版面、数字化图书插图元素、满文古籍词检测（`yolo_fourbooks_v1` 是"四书"满文词，非绘本）。Roboflow Universe 有社区书本数据集，但同为书封/书脊向，且推理走其云端 API。

**根因**：本项目的问题不是"认不出书"，而是"这个角度、这个光照下的摊开绘本不在任何现成数据集的分布里"。

### 3.4 绝对色差（否决）、色差方差（采用，但仅用于搜索排序）

- **绝对色差不可用**：在这盏灯下书页与桌面**都是同一种浅粉白**。证据：轮廓法找书页框（`detect_candidate_boxes`）在真实帧上只给出两个候选——整个画面、和顶部一块——两者都不是书页。人眼也难以分辨书页下缘与垫纸的边界。
- **色差方差可用**：书页上的插图强饱和，而页、桌面、显示器边框低饱和。**对灯光偏色免疫**（比的是方差不是色相）。
- 实现为 `saliency_thirds()`（饱和度均值 + 标准差 + 局部边缘能量，缩样到 96×72），**只用于给搜索排序，绝不作为检测**——显示器显示彩色内容时它的得分同样高。

## 4. 修掉的 7 个缺陷（每个都有实测证据）

### 缺陷 1：目标贴边时电机冻结，且搜索永不触发

```python
if bbox is not None:
    self._last_found_at = now          # ← 只要找到就刷新
elif now - self._last_found_at < self.hold_seconds:
    ... centred_hold                   # ← 框被裁切时此分支恒成立
else:
    ... 扫描                           # ← 因此永远到不了
```

**现象**：书被推到画面左侧一半在外，电机 0 速不动。
**修法**：只有**未被裁切**的观测才算"found"；贴边时改为**继续伺服**（贴边框的可见中心偏向被裁一侧，所以该方向自纠正），并设 2×hold 的预算上限。

### 缺陷 2：`edge_recentre` 的 PID 无限幅、且推了不见好还在推

**现象**：3 秒内冲到 −40° 行程上限（`vel=-59.9`），而目标**全程仍被裁切**；最后停在书的另一侧。
**修法**：改走与常规跟随相同的**限幅（单步 ≤8°）+ 测量验证**通道；另加**卡滞保护**——连续 3 次修正无改善即放弃，交给搜索。

### 缺陷 3：每 2 秒重置锚点 → 伺服追自己的测量噪声

**现象**：`err` 持续摆 ±0.07、电机在 ±11° 之间游走、`vel` 一直 ±2~3，永不静止。锚点框边缘逐次实测可差 **0.07~0.17（≈3~7.6°）**。
**修法**：来源粘滞（同一来源连续失手 3 次才释放）+ 锚点平滑（半程混入）+ 离群拒绝（跳变需连续 2 次一致才采纳）+ 已居中时不再重置锚点（仅保留 12 秒体检）。
**实测**：`err` 从 ±0.07 收敛到 −0.05 并冻结 70 秒以上；t=64s 的体检刷新**触发但没有踢动伺服**（框只差 0.01）。

### 缺陷 4：`validate_hold` 让电机冻结 36 秒

**现象**：`t=18s→t=54s` 电机完全不动（`motor=+20 vel=0 score=0.000`）。云端单次 1.5 s、每 2 s 发一次，"检测在飞"几乎恒真。
**修法**：等待**限时 2 秒**，超时即让边缘/搜索逻辑接管。

### 缺陷 5：搜索范围实际只有 ±20°，与配置无关

```python
candidates += [centre - 2.0 * step, centre + 2.0 * step]   # 第一轮最多 ±2×step
```

**根因**：搜索半径恒为 `2 × scan_step_degrees = 20°`，**与 `envelope_degrees` / `search_degrees` / `travel_degrees` 完全无关**，±40° 行程一直白费。
**实证**：扫掠 ±40° 后发现书就在 **−40°**，而搜索只到 ±20°。
**修法**：第一轮巡遍整个 envelope（从中心向外）；`search_degrees` 默认改为跟随 `travel_degrees`。
**验证**：实测已覆盖 `0, ±10, ±20, ±30, ±40`。

### 缺陷 6：零分扫描结束后驻留不动（含一个潜在崩溃）

**现象**：整轮扫描每个采样点都得 0 分时，会停在 `best_degrees`（=0）不动，60 秒不再尝试。
**修法**：改为**相位偏移半步重扫**（覆盖中间角度），上限 2 次后交给"请移动书本"升级。
**顺带修掉**：对**已完成**的扫描再调用 `record()` 会抛 `ValueError`——而下一次 pick 恰好会走到那里（潜在崩溃）。

### 缺陷 7：未确认的追踪框被永远跟随（"自信地对错的东西居中"）

**现象**：60 秒内**没有任何一次成功检测**（`score=0.000`），CSRT 框漂到**笔记本电脑和贴纸**上，而系统照旧上报 `centered: true`、`J1: CENTER`；快照证明画面里根本没有书。
**修法**：**信任门控**——若 18 秒内无任何检测器确认，作废追踪框（`_tracker=None`）并释放陈旧锚点，交给搜索（搜索此时已修好）。
**门限选择**：18 s 必须明显大于已居中时的 12 s 体检周期，否则正常跟踪会误伤自己。

## 5. 当前限制与已知缺口（如实）

1. **锚点会在不同文字块之间切换**：实测锚点在"大字故事块（宽 0.60~0.69, score 0.18~0.20）"与"较小文字块（宽 0.43, score 0.09）"之间来回，切换时瞄准点移动约 0.14（≈6°），**一步瞄准即可重新收敛**，但每次刷新会有一次小动作。根因是本地检测器只给文字位置、无"哪个才是正文"的语义。
2. **J1 只能水平转**：书比视野宽时（本机实测常见）右页会被切掉，J1 无解；页面纵向裁切同样无解。需要 J3/J4 的距离/竖直自由度。
3. **PP-OCR 只做检测不做识别**，所以走本地路径时不产出 `page_text`（会让阅读流程多一次云端调用）。可用 `text_recognition_crnn` 补上。
4. **两轴（J3/J4）尚未安装**，因此未做竖直标定。`lamp_core/camera_kinematics.py` 已具备多关节 2 自由度求解器（`minimum_norm_correction`），且在关节无法独立控制两轴时会**主动拒绝**（`determinant <= 1e-12`）——这正是"只用 J1"的数学表述。装好后需要：① 逐关节实测水平/竖直增益（默认模型是理想仿真值，文件里已注明）；② 竖直像素/弧度随俯仰角变化，至少测 2~3 个位置；③ 把实时跟随器改为调用该求解器。
5. **`error_y` 已测量但未使用**（已在 `/alignment.json` 里）。

## 6. 数据采集（供后续微调 YOLO）

- 工具：`collect_book_dataset.py` —— **每个角度等编码器 rpm=0 且位置进入容差才拍**（拖影是文字检测的头号杀手），输出帧 + `manifest.json`，且**不画任何调试叠加层**（否则烧进画面的 HUD 文字会被检测器当成书页文字——这是早期实测踩过的坑）。
- 已采集：`datasets/` 下 13 批共 **60 帧**（其中一批是系统扫掠：13 个角度 ×3 帧；其余为位移/搜索测试的单帧）。
- ⚠️ **重要陷阱**：采集器每次启动都会 `set_zero_point`，所以 `--angles=25` 再 `--angles=-25` **不是回到原位**，而是从漂移后的位置再转 −25°。早期用这个方法做"位移测试"导致镜头累计偏离 40° 以上，并让我一度误判。做位移测试请先记录绝对角度。
- ⚠️ `--angles` 取负数必须写成 `--angles=-40,-30,...`（argparse 会把 `-40` 当选项）。
- 辅助工具：`report_dataset_frames.py`（报告每帧的文字检测与锚点面积，用来从扫掠里定位书在哪个角度）。
- 自动标注思路：用云端 VLM 的 `locate_page` 给书页框作标签，PP-OCR 交叉校验（文字框应落在页框内），再由人/模型逐图复核。

## 8. 供评阅的具体问题

1. **`_pick_candidate` 是否过于臃肿**？它现在同时处理来源粘滞、离群拒绝、尺寸校验、锁与状态机，是否应拆成"候选生成 / 候选校验 / 采纳"三层？
2. **锚点在文字块之间切换**（限制 1）本地可有解？例如：优先选面积最大的块并锁定它、或对锚点做跨帧关联（重叠最大者续用）。是否值得？
3. **信任门控的 18 秒**是否合理？更稳的做法是要求"连续 N 次确认"而非固定时长吗？
4. **直接瞄准的 8° 单步上限**与 0.8 s 等待，是否该由实测的电机加减速曲线推导，而不是取常数？
5. **`update()` 的分支顺序**（`fully_visible` → `validate_hold` → `edge_recentre` → `centred_hold` → `scan`）是否还有互斥/饥饿隐患？
6. **测试覆盖的薄弱处**：捕获循环 `_capture_loop` 仍无集成测试（本轮就是靠它暴露了一个属性名错误 `self.follower` vs `self.j1_follower`）。是否值得引入一个假的 picamera2 做端到端测试？
7. **是否需要把常数集中**（`44.5` / `0.03` / `8.0` / `18.0` / `2.0` / `1.5` 等散落在两个文件里）为一处标定配置？

## 12. Codex 复核后的改进（2026-09-15）

已完整复核本轮源码、测试、工具与本文档，并参考 OpenCV Zoo、YOLOX、
Ultralytics COCO/树莓派部署以及 Norfair 的公开实现。结论修正如下：

- “YOLO Nano 没有书本训练结果”不准确。COCO 80 类明确包含 `book`（类别
  73），COCO 预训练的 YOLO/YOLOX Nano 均学过书本；真正的问题是摊开、
  裁边、俯视绘本与 COCO 普通书本图片之间存在明显域差异。本机 0.37 左右的
  实测分数说明它不能单独担任最终裁决，但仍适合作为本地语义证据，与 OCR、
  页面几何共同融合。
- 文字锚点新增跨帧关联：优先续接与上一锚点 IoU/中心距离一致的文字块，不再
  每轮重新选择面积最大的段落；找到包围文字的可靠页面轮廓时，跟随页面中心。
- 有云端语义客户端时，PP-OCR 只负责产生“值得检查”的候选，首次获取必须通过
  语义确认，防止笔记本、屏幕或包装文字自行刷新信任时间。无云模式保留明确的
  降级路径。
- J1 默认直接瞄准改为 `CoarseToFineAim`：大误差近似一步到位，小误差逐渐降低
  增益；中心使用滞回锁定；小幅反向需要连续确认，从控制源头抑制最后阶段的
  左右摆动，而不是依赖 PID 不断追踪噪声。
- 边缘卡滞只按真实修正动作计数，不再按视频帧计数；扫描目标切换时按实际最大
  输出速度估算到达时间，移动期间返回的旧检测不再错误记到新角度。
- detector worker 增加 generation，`reset()` 后旧网络请求即使返回也不能恢复旧框；
  锚点状态统一在锁内提交。
- 普通启动与网页 reset 不再发送 `set_zero_point`。使用实时 accumulated encoder
  作为 session anchor，避免多次重启逐渐移动安全包络。
- `locate_page()` 现在校验模型实际返回的 confidence；命令行 checksum 选项与
  `ChecksumMode` 枚举保持一致。

验证结果：相关专项测试从 161 增至 175；项目全量测试 330 个全部通过；
`compileall` 与 `git diff --check` 通过。真机连续跟踪仍需在停止旧预览服务、同步
代码后单独执行，不能用离线测试代替。

### 12.1 2026-09-16 首轮真机闭环发现与修复

首次真机启动后，系统成功锁定丹麦语绘本并在 `-14.8°`、水平误差 `-1.2%`
短暂停稳；下一次框刷新后，控制状态却从 `edge_recentre` 错误进入
`narrowing_scan`，目标依次走到 `-10°`、`-20°`、`+20°`。根因是控制层将上下
裁边也视为 J1 可修复的裁边，并且边缘修正预算结束后，即使可信框仍存在也会
落入盲扫。

修复后仅左右裁边触发 J1 拉回；只要可信绘本框仍存在，预算用完便进入
`visible_hold`，绝不启动盲扫。只有目标框真正丢失或超过信任门控时才允许搜索。

第二轮真机闭环中，重新锁定后连续 24 秒保持 `book_follow`；水平误差稳定在
`0.1%~0.36%`，J1 固定在 `-12.59°`、速度为零，`pick_count` 从 11 更新到 12
也未跳框或回摆。停止测试时另发现 MJPEG 客户端可令 HTTP 服务退出等待形成
死锁；现已让 `stop()` 主动结束视频流，并在 `server_close()` 前停止摄像头，
HTTP 客户端线程也改为 daemon，确保网页停止按钮与 SIGTERM 可以可靠退出。
纯摄像头复测在保持 MJPEG 客户端连接的情况下，systemd 正常停止耗时 `1.92 s`，
服务进入 `inactive`，无需再发送 SIGKILL。

第三轮重启测试发现：全画面语义重定位连续两次选中同一错误区域后，旧的“两次
确认”仍会接受跳变框，J1 因此从 `+4°` 被拉向 `+40°` 软件边界。现在健康的
云端/CSRT 跟踪只会把当前实时框（带 10% 上下文）裁出，调用语义模型确认该
裁图是否仍为绘本；确认成功仅刷新信任时间，绝不重写坐标。连续三次裁图确认
失败才丢弃 tracker，随后才允许全画面重新搜索。

第四轮真机测试将搜索和运行包络临时限制为 `±10°`。系统独立获取绘本后，连续
约 45 秒保持 `book_follow`；水平误差稳定在 `-1.8%~-2.5%`，J1 目标保持
`+10°`、速度为零，`pick_count` 从 3 增至 10、`api_miss_count` 始终为零。
这证明多轮云端裁图确认只刷新了信任状态，没有再次覆盖 CSRT 坐标，也没有触发
反向回摆或搜索。测试随后通过网页 `/shutdown` 正常停止。
